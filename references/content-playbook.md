## Source discipline

Create a source ledger before planning slides:

| Category | Required evidence |
| --- | --- |
| Current product | working prototype, tested device, screenshots, code or demo evidence |
| Current traction | signed customers, paid users, revenue, pilots, letters of intent |
| Pending work | patents being prepared, tests not yet run, certifications in progress |
| Targets | planned users, revenue, partnerships, social impact, future scenarios |
| Market data | exact figure, year, population, methodology, and named source |
| Deprecated data | figures or claims the user has explicitly rejected |

When sources conflict, use the newest designated project source and ask only if the conflict changes the deck's central claim. Mark unsupported statements as an assumption or remove them. Never convert a target into an achievement.

When a reference deck exists, separate the attributes:

- **Content reference:** page order, argument structure, density, named examples, business logic, data points, and level of explanation.
- **Title reference:** how much information the title carries and whether it names a product position or only a section.
- **Language reference:** sentence length, amount of explanation, use of numbers, and level of formality.
- **Visual reference:** palette, imagery, chart style, typography, and page composition.

Borrow only the attributes the user authorized. If they say “content and title style only,” do not copy the reference palette or layout.

## One-sentence positioning

The opening sentence should answer four questions without sounding like a taxonomy:

1. What kind of product is it?
2. Whom does it serve?
3. What process or problem does it understand?
4. What outcome does it change?

Strong structure:

> [Product] is a [technology-driven category] for [specific audience] that [changes a concrete process].

Avoid opening with a list of model names, a vague “AI empowers everything” claim, or a category phrase that the audience cannot visualize. If the user wants an ambitious framing, make the ambition come from the change in the user's workflow, not from inflated adjectives.

## Narrative architecture

A reliable 20–26 page pitch follows this order unless the brief requires another:

1. Cover
2. Contents
3. Why now: technology or behavior shift
4. Market or audience context
5. Real user problem
6. Product thesis and ideal outcome
7. Product architecture or capability chain
8. Capture and input
9. Understanding or event recognition
10. The core user payoff
11. Long-term memory or personalization
12. Product forms
13. User journey
14. Interface or interaction evidence
15. Competitive position
16. Business model
17. Consumer offer
18. Industry offer
19. Growth path
20. Named partnership targets
21. Financial plan
22. Team and current results
23. Social value
24. Long-term roadmap
25. Closing

This order answers the audience's questions in sequence: why should I care, what is it, how does it work, can users understand it, can it make money, who will help it scale, and why is this team credible?

## Page-level content rules

- Put one conclusion in the large page title.
- Use a short four-character section label when the user wants stable top-level navigation.
- Give each page one audience move: from not knowing to understanding, from skepticism to belief, from interest to action.
- Use a short paragraph or three connected statements below the title. Do not fill the page with every fact from the source.
- Place source notes in a small footer when the page contains external figures.
- Use the same title position, body start, and footer baseline across the deck.
- Keep the section title visible but let the product image or data evidence dominate.

## Product and technology writing

Describe the product in this order:

1. Ideal outcome in ordinary language.
2. Product forms: app, phone, dedicated device, web service, or hardware ecosystem.
3. Interaction loop: what the user starts, what the system captures, what it returns, and what the user can do next.
4. User value: replay, diagnosis, error correction, organization, knowledge map, review plan, or another concrete output.
5. Core technologies and the specific failure each one prevents.
6. Final one-sentence summary.

For each core technology, write:

> **Technology name:** [professional term or architecture]. It solves [specific failure mode], so the user gets [observable outcome].

Use the technical term only when it helps an informed judge understand defensibility. Immediately explain the user consequence. Avoid self-invented phrases that sound academic but do not correspond to a recognizable method.

For intellectual property:

- Say “preparing to file” when applications are not submitted.
- Say “pending” only when an application exists.
- Never say “authorized” without a granted patent number.
- Group patents by the process chain they protect, not as an unstructured logo wall.

## Business, partner, and future writing

Business slides need names and arithmetic:

- Consumer price and billing period.
- Enterprise price per device, per call, or annual framework.
- POC fee or free-pilot terms.
- Current signed status separately from target partners.
- Revenue goals by year and the user/partner assumptions behind them.

Partner slides should answer:

- Why these companies specifically?
- What product or channel does each one bring?
- What is the first collaboration unit?
- What would the first joint case prove?

State that partners are targets until a signed agreement exists.

Financial slides should use one planning basis. Show the funding request, allocation, milestone, and what evidence the milestone buys. Do not mix market size, revenue target, and valuation in one visual.

Team slides should separate:

- Adviser versus student team.
- Named responsibilities.
- Current prototype and test evidence.
- Patent or publication status.
- Work still required before launch.

Future and social-value slides may be ambitious, but say “goal,” “hope,” or “long-term direction.” Describe the ideal state vividly, then keep the current baseline honest.

## Chinese copy standards

- Write complete sentences. A phrase such as “过程感知—证据链—智能体” is a label, not an explanation.
- Reduce nested abstractions. Replace “多源异构协同赋能” with a concrete actor, action, and result.
- Use parallelism sparingly. Three balanced slogans in a row usually make the slide feel generated.
- Remove empty transitions such as “综上所述”“值得注意的是”“不仅……而且……” when they do not add logic.
- Keep English technical terms only where the user or domain genuinely uses them.
- Read the slide aloud. If it cannot be said naturally in a presentation, rewrite it.
